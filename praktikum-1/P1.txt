### 2. Fugen Sie einen weiteren Client (basierend auf der vorherigen Aufgabe) zum Projekt hinzu, der einen connected UDP socket benutzt. Welche Auswirkungen hat dies?*
The connected UDP client uses `connect()` to associate the socket with a specific remote IP address and port. Consequently, `send()` and `recv()` can be used instead of `sendto()` and `recvfrom()`, simplifying the code. The socket normally receives datagrams only from the configured peer. However, UDP remains connectionless at the transport protocol level: `connect()` does not establish a handshake or guarantee reliable delivery. Both clients successfully received the 9216-byte echo message in our test.
A connected UDP socket also reports ICMP errors to the application. Without a running server, the unconnected client waited in `recvfrom()` without receiving an error, while the connected client terminated with `recv: Connection refused` (ICMP port unreachable). We observed the same behavior on Linux (WSL) and FreeBSD.

### 3. Was passiert, wenn der Client sehr große Pakete schicken will? Warum?*
When sending very large messages using UDP, the transmission may fail if the datagram exceeds the maximum size supported by IPv4 or the system. The limit depends on the system. Results of our experiment through localhost:

Size	Linux (WSL)	FreeBSD 15.1
9216	Received	Received
9217	Received	Message too long
60000	Received	Message too long
65507	Received	Message too long
65508	Message too long	Message too long

The maximum UDP payload over IPv4 is 65535 - 20 (IPv4 header) - 8 (UDP header) = 65507 bytes, so 65508 bytes fail on both systems. FreeBSD limits outgoing datagrams earlier: `sysctl net.inet.udp.maxdgram` is 9216 bytes.
Large UDP datagrams may also require IP fragmentation when they exceed the network MTU. If a fragment is lost, the complete datagram cannot be reassembled and delivered to the application. Unlike TCP, UDP does not provide automatic retransmission or reliable delivery.


### 4. Stellen Sie die Kommunikation auf UDP-Lite um. Erweitern Sie den Client und den Server, so dass die Send und Receive Checksum Coverage uber Kommandozeilenargumente konfigurierbar sind. Testen Sie wesentliche Kombinationen dieser Parameter.
Im Rahmen dieser Aufgabe wurde das ursprüngliche UDP-Echo-Programm so angepasst, dass es das Protokoll UDP-Lite verwendet. Dazu wurde beim Stellen der Sockets das Protokoll `IPPROTO_UDPLITE` angegeben.
Mit den Socket-Optionen `UDPLITE_SEND_CSCOV` und `UDPLITE_RECV_CSCOV` kann die Checksum-Coverage beim Senden und Empfangen konfiguriert werden. Die Werte werden über Kommandozeilenargumente übergeben, sodass unterschiedliche Einstellungen ohne Änderungen am Quellcode getestet werden können.
The Server empfängt Datagramme and sendet sie anschließend an den jeweiligen Client zurück. Mit `getsockopt()` wird überprüft, welcher Wert für die Empfangs-Coverage tatsächlich gespeichert wurde.
Bei den Tests mit einer Empfangs-Coverage von 8 wurden Datagramme mit den Send-Coverage-Werten 100, 9216 und 0 erfolgreich empfangen. Bei einer Empfangs-Coverage von 0 wurden dagegen nur Datagramme mit vollständiger Coverage empfangen; ein Test mit partieller Coverage lieferte keine Antwort.
Dies ist das erwartete Verhalten. Die Empfangs-Coverage ist ein Mindestwert: Ein Datagramm mit partieller Coverage wird nur angenommen, wenn seine Coverage mindestens so groß ist. Der Wert 0 verlangt die vollständige Coverage, daher verwirft der Kernel Datagramme mit partieller Coverage ohne Fehlermeldung, und der Client wartet weiter. Datagramme mit vollständiger Coverage werden immer angenommen. Beim Senden bedeutet 0 vollständige Coverage.
Das Datagramm hat 9216 Byte Daten + 8 Byte UDP-Lite-Header = 9224 Byte. Deshalb ist 9223 noch eine partielle und 9224 die vollständige Coverage.
Die Option wirkt in beide Richtungen: Bei Server `8 0` und Client `0 0` empfängt der Server das Datagramm, aber der Client verwirft die Antwort.
Die Werte der Optionen unterscheiden sich: Linux verwendet 10 (SEND) und 11 (RECV), FreeBSD 2 und 4 (`<netinet/udplite.h>`). Mit den Linux-Werten meldet FreeBSD `setsockopt UDPLITE_SEND_CSCOV: Protocol not available`.
